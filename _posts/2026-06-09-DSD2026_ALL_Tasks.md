## 1. Software Requirements Specification (System Level)

This document defines the system-level software requirements for the Limb Motion Recognition and Assistant system, a distributed rehabilitation platform jointly developed by UTAD (Portugal) and Jilin University (China) under the DSD 2025–2026 programme. The specification covers seven core use cases (UC-01 to UC-07) including user registration, user login, sensor connection, start rehabilitation session, receive real-time motion feedback, review patient progress, and prescribe exercise plan. The document establishes the system architecture across three layers (Sensor Layer, Server Layer, Monitor Layer), defines interface contracts (IF1 for sensor-to-server, IF2 for server-to-monitor), and specifies team responsibilities for all six development teams. It supports two deployment contexts: clinical setting (supervised, stable network) and home setting (independent, potentially unstable network with local buffering).

## 2. Software Requirements Specification — M1 Patient Mobile App

This M1-specific SRS document specialises the system-level requirements for the Patient Mobile Application, which is responsible for user interaction, real-time motion visualisation, posture correction alerts, session management, and Bluetooth/BLE sensor connectivity. The specification defines twelve M1-specific use cases (UC-M1-01 to UC-M1-12) covering register, login, sensor connection, start session, real-time feedback, posture alerts, end session, view history, view plan, achievements, push notifications, and logout. The document clarifies M1's scope boundaries (in-scope and out-of-scope), details the IF2 interface requirements for consuming backend services via REST and WebSocket protocols, and aligns M1's functional and non-functional requirements with the overall system architecture. M1 co-owns the IF2 contract with Team V2, which must be frozen by the end of Sprint 2.

## 4. M1 Interface Specification

This technical specification defines all seven interface contracts that cross the M1 module boundary, covering data exchange between M1 and V2 Backend (IF-V2-M1 for input, IF-M1-V2 for output), sensor layer interactions (IF-S1-M1 for raw IMU data, IF-M1-S2 for session control commands, IF-S2-M1 for formatted sensor data), and push notification services (IF-Push-M1 for incoming notifications, IF-M1-Push for device token registration). The document specifies API endpoints with request/response formats (GET /users/:id, POST /sessions, PATCH /sessions/:id/end, etc.), data structures (User, Session, Measurement, SensorSample, TargetAngle, etc.), communication methods (HTTP REST API, Bluetooth Low Energy, Function Call), and error handling approaches. It serves as the authoritative reference for M1's integration points with other system modules and external services, ensuring smooth data flow across the distributed rehabilitation platform.

The work involved configuring Firebase SDK by adding google-services.json to the app directory, modifying app/build.gradle.kts and project root build.gradle.kts for Firebase dependencies (firebase-bom:33.5.0, firebase-messaging), creating FcmService.kt to handle onNewToken() for token management and onMessageReceived() for notification display, integrating FCM token retrieval in LoginViewModel.kt on login success, and registering the service in AndroidManifest.xml with intent filter for FCM events. ## Task 7: Progress Page - Real Data Integration

Integrated real backend API data into the Progress page, replacing previously used mock data with live data from the V2 backend service to display actual patient rehabilitation progress. The implementation involved adding GET /progress/{userId} API method in V2ApiClient.kt with ProgressDto data class for parsing API response (weeklyRom, weeklyPain, adherencePct, streakDays), creating loadProgress() function in ProgressViewModel.kt using Kotlin coroutines (viewModelScope.launch), and binding API responses to UI components (LineChartView for ROM trends, DonutChartView for adherence percentage) via LiveData/StateFlow. ## 2. Core Code Development: SessionController and LegView

**Date:** N/A (spanning Phase I and Phase II)  
**Status:** Completed

### Description
Developed two core architectural components for the M1 Android application: **SessionController** (business logic layer) and **LegView** (custom visualization UI). Simultaneously, extended and adapted the V2 backend integration layer to support batch measurement uploads and WebSocket real-time feedback.

### 2.1 SessionController — Session Lifecycle and Data Pipeline

A singleton controller that encapsulates the entire lifecycle of a rehabilitation training session, bridging the S2 sensor processing layer and the V2 cloud backend.

**Architecture and Responsibilities:**
- **State Machine:** Manages session states (`IDLE → RUNNING ↔ PAUSED → ENDED → IDLE`), enforcing strict state transition validation to prevent illegal operations (e.g., stopping a session when in idle state).
- **Three Concurrent 10 Hz Loops:**
  1. **Read Loop:** Polls the S2 module (`s2.data.read()`) every 100 ms, caches `FormatData` blocks in memory, and appends them to the upload queue.
  2. **Upload Loop:** Sends data from the upload queue to V2 in batches (`uploadMeasurementsBatch()`). On failure, automatically retries by re-enqueuing at the head of the queue to preserve order.
  3. **Download Loop:** Polls V2 every 15 seconds for real-time AI recommendations (`getSessionRecommendations`), caching results for UI consumption.
- **Data Transformation:** Converts internal `FormatData` (joint angles, sensor samples, error events) into V2-compatible JSON payloads, with timestamps in ISO-8601 UTC format.
- **Rich Access Interface:** Provides thread-safe getter methods, including latest data, cumulative statistics (sample / angle / error counts), full local cache, and AI recommendations.
- **Sensor Mode Switching:** Supports runtime switching between real BLE sensors (`S1RealModule`) and simulated fallback (`SimulatedS1Module`).

**Key Integrated APIs:**
- `V2ApiClient.createSession()` / `endSession()` — Session lifecycle management.
- `V2ApiClient.uploadMeasurementsBatch()` — Batch upload of rehabilitation measurements.
- `V2ApiClient.getSessionRecommendations()` — AI feedback retrieval.

### 2.2 LegView — Leg Visualization

A custom `View` component for real-time rendering of a leg model, providing rehabilitation training feedback.

**Features:**
- **Dual-leg Support:** Left and right legs maintain independent animation states, each managing its own `LegState` (target angle queue, rendered angle, `ValueAnimator`).
- **Three Display Modes:**
  - `HORIZONTAL` — Supine position (hip joint fixed, ankle joints on the same horizontal line).
  - `SQUAT` — Squat motion (ankle joints fixed, hip joint moves vertically).
  - `STEPPING` — Stepping / walking motion (hip joint fixed, lower legs vertical downward).
- **Adaptive Animation:** When the angle queue exceeds 10 items, a backpressure protection mechanism drops intermediate frames to ensure the UI always catches up to the latest sensor values. Animation duration scales inversely with queue depth (120 ms → 20 ms).
- **Rendering:** Uses `Canvas` path drawing, constructing organic limb shapes via cubic Bézier curves; `LinearGradient` for 3D cylindrical shading effects, and `RadialGradient` for spherical knee-joint highlights.
- **Dynamic Scaling:** `onSizeChanged()` computes proportional geometric parameters based on view dimensions, ensuring the leg model remains within safe margins across different screen sizes.
- **Configurable Appearance:** Supports per-leg gradient colors (limb + knee) and visibility toggling.

### 2.3 V2 Backend Interface Adaptation

- **Batch Upload:** Implemented `uploadMeasurementsBatch()`, sending accumulated sensor data in batches rather than per-request, reducing network overhead.
- **WebSocket Integration:** Adapted the session controller to support WSS (`wss://.../ws?sessionId=<id>`) real-time server-push feedback, replacing the legacy polling mechanism for real-time motion feedback.
- **Data Format Alignment:** Ensured the `FormatData → JSON` mapping complies with V2 API requirements, including `jointAngles`, `sensorData` (accelerometer / gyroscope / roll-pitch-yaw), and the `errors` array.

  - Enables end-to-end validation of the V2 data pipeline without physical hardware.
- **V2 Data Transmission Validation:** Used the simulated sensor to verify:
  - Session creation and termination via REST.
  - Integrity and ordering of batch measurement uploads.
  - Reception and parsing of WebSocket real-time feedback (`movement_feedback` messages).
